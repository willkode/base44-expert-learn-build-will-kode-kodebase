# Client Portal & White-Label Delivery System — Prompt Series

A sequential, copy-paste-ready prompt series for building the client-facing half of a service business: a branded client portal with project status, milestone sign-offs, file delivery and approvals, feedback threads, invoicing view — plus a white-label mode for agency resale.

**How to use:** Run the prompts in order. The core portal is Prompts 1–8; white-label and advanced features are Prompts 9–13. Pairs naturally with the Vibe Coding Business OS (internal side).

---

## Prompt 1 — Scan & Portal Blueprint

```
Scan my entire app before making changes. Document: existing entities (especially any project, client, task, or invoice entities), user roles, routes, and the design system.

Then produce a client portal blueprint:
- What clients will see: project status, milestones, files, feedback, invoices
- How client users differ from internal users (roles and access boundaries)
- Which existing entities we can reuse vs. what's missing
- The portal's route structure (e.g. /portal, /portal/projects/:id)

Rule: clients must NEVER see internal data — other clients' projects, internal notes, costs/margins, or admin tools. List every boundary explicitly. Do not build anything yet.
```

**Acceptance criteria:** A written blueprint with explicit client data boundaries. Nothing built yet.

---

## Prompt 2 — Client Role & Data Foundation

```
Create the data foundation:

1. Add a "client" user role (keep existing roles unchanged).
2. A ClientProject entity (or extend my existing project entity): name, description, status (planning/in_progress/review/completed), clientUserIds (array), startDate, targetDate, coverImageUrl.
3. A Milestone entity: projectId, title, description, order, status (upcoming/in_progress/delivered/approved), deliveredAt, approvedAt, clientNote.
4. A ProjectFile entity: projectId, milestoneId (optional), fileName, fileUri (PRIVATE storage), version, status (delivered/approved/revision_requested), uploadedBy.

Security rules (critical):
- Clients can read ONLY projects where their userId is in clientUserIds — and everything (milestones, files) scoped to those projects.
- Clients can update ONLY approval/feedback fields, never core project data.
- Admins have full access.

Show me the access rules for each entity when done.
```

**Acceptance criteria:** Entities exist; a client user can only ever see their own projects' data.

---

## Prompt 3 — Client Portal Shell & Dashboard

```
Build the client portal shell:

1. A /portal layout: clean branded header with my logo and colors, simple nav (Projects, Files, Invoices, Help), and the client's name with a logout option. No internal app navigation may leak in.
2. Route protection: only authenticated users with the client role (or admins previewing) can access /portal routes; others are redirected.
3. The portal dashboard: a welcome header, cards for each of the client's projects showing name, status badge, progress (approved milestones / total), and next upcoming milestone.
4. Empty state for clients with no projects yet ("Your projects will appear here soon").

Reuse my design tokens but keep the portal visually calmer than the internal app — this is what paying clients see.
```

**Acceptance criteria:** Clients land in a branded portal listing only their projects.

---

## Prompt 4 — Project Detail & Milestone Timeline

```
Build the client project detail page (/portal/projects/:id):

1. Header: project name, status, dates, and overall progress bar.
2. A vertical milestone timeline: each milestone shows title, description, status, and dates — visually distinguishing completed, current, and upcoming.
3. Milestones with "delivered" status show their attached files and an approval action (built next prompt).
4. Access check: if the client doesn't belong to this project, show "not found" — never a permission error revealing the project exists.
5. Mobile: the timeline must read cleanly on a phone.
```

**Acceptance criteria:** Clients see a clear timeline of their real project; foreign project IDs show not-found.

---

## Prompt 5 — File Delivery & Approval Workflow

```
Build the delivery and approval workflow:

1. Admin side: on a milestone, upload deliverable files to PRIVATE storage and mark the milestone "delivered". Support multiple files and versioning (v2 replaces v1 visually but keeps history).
2. Client side: delivered milestones show the files with secure download buttons (signed URLs generated by a backend function that verifies the client belongs to the project).
3. Approval: the client can "Approve milestone" (with optional comment) or "Request changes" (comment required). Approving sets approvedAt; requesting changes flips the milestone back to in_progress with the note visible to the admin.
4. Confirmation dialog before approval: "Approving confirms this milestone is complete."
5. Notify the admin by email on both approval and change requests.
```

**Acceptance criteria:** Full deliver → review → approve/request-changes loop works with secure downloads and notifications.

---

## Prompt 6 — Feedback Threads

```
Add scoped feedback threads:

1. A FeedbackMessage entity: projectId, milestoneId (optional), authorId, authorRole (client/admin), message, createdAt. Clients read/write only within their own projects.
2. A discussion thread on each milestone: chronological messages with author name, role badge, and timestamp; input box with send button.
3. A project-level "General discussion" thread for anything not tied to a milestone.
4. Unread indicators: show a dot on threads with messages the current user hasn't seen.
5. Email notification to the other party when a new message is posted (throttled: max one email per thread per hour).
```

**Acceptance criteria:** Clients and admin can converse per milestone; notifications fire without spamming.

---

## Prompt 7 — Client Invoicing View

```
Add the invoicing view to the portal:

1. An Invoice entity (or reuse my existing one): projectId, clientUserIds, invoiceNumber, description, amountCents, currency, status (draft/sent/paid/overdue), dueDate, paidAt, paymentLinkUrl. Clients read only their own; admin-only write.
2. A /portal/invoices page: table of the client's invoices with number, project, amount, due date, and a clear status badge.
3. Unpaid invoices show a "Pay now" button linking to the paymentLinkUrl if present.
4. An invoice detail view with line description and payment history.
5. Admin side: a simple invoice manager to create/send invoices per project (mark-as-paid manually is fine for the MVP).
```

**Acceptance criteria:** Clients see and can act on only their own invoices.

---

## Prompt 8 — Core Audit (End of Core Portal)

```
Audit the portal before white-labeling:

- Isolation: log in as client A and try to reach client B's projects, files, invoices, and threads via direct URLs and API calls. Everything must fail closed.
- Role test: a client must never see internal routes, admin nav, or internal-only fields (costs, internal notes).
- Signed URL test: file links must expire and must not work for non-members.
- Flow test: full journey — admin creates project + milestones, delivers files, client reviews, requests changes, admin redelivers, client approves, invoice sent and viewed. On mobile too.

Fix everything found and report what was tested.
```

**Acceptance criteria:** Documented audit; all isolation tests fail closed.

## Prompt 9 — White-Label Mode (Advanced)

```
Add white-label branding:

1. A PortalBranding entity (admin-only write): companyName, logoUrl, faviconUrl, primaryColor, accentColor, emailFromName, portalWelcomeMessage, supportEmail.
2. The entire /portal experience reads from PortalBranding: logo, colors (applied via CSS variables), welcome copy, and the from-name on all portal notification emails.
3. An /admin/portal-branding settings page with live preview: upload logo, pick colors, edit copy, save.
4. Default gracefully to my own branding when nothing is configured.

Result: the portal can be completely rebranded without touching code — ready to resell to my own clients.
```

---

## Prompt 10 — Client Onboarding & Invites (Advanced)

```
Build client onboarding:

1. Admin flow: from a project, "Invite client" — enter email, select role client, send the invite with a branded email explaining what the portal is.
2. First-login experience for clients: a short welcome screen (from PortalBranding welcome message) explaining status, approvals, files, and where to ask questions.
3. Multi-contact support: multiple client users per project (e.g. the client's whole team).
4. Admin view of pending invites per project with re-send capability.
```

---

## Prompt 11 — Status Digest Automation (Advanced)

```
Add automated client communication:

1. A weekly scheduled automation that emails each active client a branded project digest: milestones completed this week, what's in progress, what's next, and any items waiting on THEM (pending approvals, unanswered questions).
2. Only send when there's something to report — no empty digests.
3. An admin toggle per project to enable/disable digests, plus a preview button that renders the next digest without sending.
4. "Waiting on you" items should also surface as a banner in the client's portal dashboard.
```

---

## Prompt 12 — Change Request System (Advanced)

```
Add scope-controlled change requests:

1. A ChangeRequest entity: projectId, requestedBy, title, description, status (submitted/reviewing/quoted/approved/declined/completed), quoteAmountCents, adminNotes (internal only).
2. Client side: a "Request a change" button on the project page with a simple form, and a list of their requests with status.
3. Admin side: review queue — respond with a quote or decline with a reason; quoted requests show the price to the client with approve/decline actions.
4. Approved change requests can be converted into a new milestone on the project in one click.

This keeps scope creep documented, priced, and out of the feedback threads.
```

---

## Prompt 13 — Final Launch Audit

```
Run the final portal launch audit:

Security: re-run all Prompt 8 isolation checks including branding settings, invites, digests, and change requests; verify internal adminNotes never reach client responses.
White-label: rebrand fully via settings and confirm zero traces of default branding anywhere (pages, emails, favicon).
Full journey: invite a fresh client → onboarding → project lifecycle → change request → invoice → digest email. Mobile and desktop.

Deliver a final report: everything tested, fixed, and remaining manual steps.
```
